# Guided onboarding and bounded demo pilot

The public `/manual` and contextual guide in `/cuenta` explain the current
company, participant, private document review, worksite, CRM and WhatsApp flows.
The guide links to visible sections and respects the current account and
organization. Its personal reading marks are temporary; they do not certify
configuration, grant permissions or send commands.

The eight-step guide includes the existing **Clientes y seguimiento** panel.
Its shortcut is available only when that authorized panel is visible; a missing
panel explains the administrator dependency. Reading marks never infer CRM
authority. Official Meta asset authorization, receiving the phone verification
code, and physical pilot acceptance remain human steps. Controlled browser and
database fixtures do not certify those external or physical steps.

## Canonical pilot boundary

The demo uses the existing app, WABA and Test Number through a trusted internal
`DEMO_PILOT` protocol capability. Customer factories retain their default
`CUSTOMER` protocol and rejection of demo assets. The pilot shares canonical
session verification, worker binding, signed durable inbox, field transactions,
private media processing, outbox and receipt recovery. There is no second field
engine, table set or credential store.

Preparation requires a dedicated empty project, the requesting administrator's
own authorized participant, KYC reviewed by another authorized person, an allowed
test recipient and two explicit confirmations. The server checks current Meta
assets and subscription without registering a number or changing provider
configuration. An encrypted grant is scoped to actor, organization, project,
worker, app and channel, lasts at most one hour and can be revoked. Demo secrets,
events and proofs use separate purposes and namespaces. Replies carry a DEMO
label. The pilot does not send proactive templates.

`/api/webhooks/whatsapp` dispatches an original HMAC-signed app body to its
canonical customer or demo protocol within one durable transaction. Unknown
channels fail closed. `/api/whatsapp` no longer executes the legacy global
handler. The existing authenticated recovery job checks one event per protocol;
explicit customer POST jobs remain customer-only. No provider tokens, app/WABA
assets, number or cron credentials are regenerated by these changes.

The browser reserves only minimal operation references in the existing native
IndexedDB journal before a POST. Reload recovery queries the exact receipt.
Unknown results retain the reference and block another send. Challenge codes
are shown only for the requested worker, only once, and only while unexpired;
neither GET recovery nor browser storage recovers them.

## Field interface corrections

Attendance controls follow the canonical recorded sequence: break must be ended
before checkout. A decided proposal displays its recorded decision instead of
presenting it as expired when the original offer deadline passes. Task progress
still changes only after a current authorized decision.

## Evidence and release states

Keep these separate in each release record:

1. **Implemented:** code and exact source revision.
2. **Technically tested:** unit, disposable PostgreSQL, controlled browser and
   provider checks, with synthetic fixtures identified.
3. **Published:** deployment revision, target and served custom domain match.
4. **Accepted:** actual authorized participants, phone delivery, private media,
   GPS/QR and business outcomes were observed in a real pilot.

CI runs default-customer regressions, isolated demo transactions and browser
receipt recovery, as well as manual and guide checks at 320/390/768/1280 pixels.
Controlled sessions, provider responses and GPS fixtures are not a real Clerk
login, WhatsApp delivery, biometric decision or physical worksite acceptance.

Production Clerk social configuration is independent of the code release.
Google requires the exact production OAuth client and return URI. Facebook and
LinkedIn require their own production provider configuration and real login
checks before being described as available.

## External prerequisites and unavailable features

Business verification, technology-provider verification, publication, App Review,
permissions and Embedded Signup configuration must satisfy Meta's actual gates.
Submitting business verification is not approval. A configured token or read-only
asset GET does not prove the callback handshake. The generic callback requires
the existing `META_VERIFY_TOKEN` to meet the canonical minimum of 32 characters;
never log or regenerate it to make a check pass. Confirm both the real handshake
and a signed message reaching its exact durable receipt before transport
acceptance. Receiving a message in WhatsApp alone is insufficient.

The callback URL is a technical Meta receiver, not an onboarding page. A bare
browser GET is an invalid verification request. Each required verification
parameter must occur exactly once; additional query parameters are ignored,
never used as identity or authority. Meta's real verification was observed with
six parameters, including three additional keys. The exact token comparison,
challenge constraints and signed POST remain mandatory. Invalid GET diagnostics
contain only fixed scalar query-shape fields, without URL or parameter values.

Private document/selfie review is human. Facial matching and liveness are not
implemented. The manual open-shift reminder is the only adopted proactive
template workflow; other catalog entries do not imply an implemented send.
Formal quotes, tenders, commercial automations and offline file/draft submission
are not part of this release. Demo preparation does not certify commercial
activation or real work.
