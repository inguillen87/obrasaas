# Material consumption feedback

After an authorized participant proposes consumption, the WhatsApp acknowledgement identifies the worksite, material, exact quantity/unit, informing time, proposal ID and receipt. It describes the saved proposal; only an independent authorized review changes stock. Replaying that delivery preserves its original acknowledgement even after later review.

`ESTADO` offers **Mis consumos**, and `CONSUMOS` opens the participant's own history. Pages contain at most five reports; selection, detail, paging and return actions retain the current conversation nonce. Detail shows the current pending/approved/rejected/reversed state and available decision/reversal reasons, timestamps and receipts. An active business draft is preserved until explicit cancellation. These queries do not approve a report or move stock, and do not introduce proactive sends.

The private reader resolves the current tenant, project assignment, participant, reporting permission and canonical approved identity before accessing report rows. Visibility requires both the current worker ID and the immutable original informing account. Reassigning a worker does not transfer history, cursor access or direct-ID access to the replacement account. The same own-reader restriction applies to administrators/directors using the personal WhatsApp route; general web review retains its existing ADMIN/DIRECTOR authorization.

New proposals save their original material name and proposal receipt with the incident, inside the existing transaction. Existing rows may omit those fields. The web labels the mutable linked worker separately from the informing account, shows available review/reversal evidence, and marks incomplete historical events as unconfirmed instead of inventing names, times or receipts. Recovery separates `recordedConsumptionSnapshot` from the current `consumption`; the original receipt and stock effect do not become a claim about a later state.

The change uses the existing organization/project/worker/incident/audit model, encrypted Meta callback/lease/bridge and recovery journal. It adds no migration, provider credentials, commercial activation or production pilot records.

When the catalog changes before a WhatsApp consumption is confirmed, the rejected command keeps its original encrypted draft, nonce, message origin and deadline. A separate encrypted recovery record binds the original deadline, current principal/context and first/latest rejection receipts. `CONSUMO`, sent in reply to the original prompt, explicitly reopens material selection. The previous amount and reason are suggestions: the participant must select a current material, confirm or reenter the amount, confirm or rewrite the reason, and use the fresh **Guardar** option. A changed unit requires a newly entered amount; no conversion or material substitution happens automatically.

Recovery never renews the draft deadline or source-event lease. Old options, invalid input, greetings and status/menu reads keep the current envelope. The existing signed identity resolver and fresh SQL clocks fence recovery and cached replies after awaited work; expiry around a save rolls its proposal and receipt back. An already committed consumption acknowledgement remains recoverable with current authority after the draft expires. Explicit cancellation clears this recovery; its earlier rejection audits remain immutable. A separate terminal cancellation receipt preserves that outcome on replay after expiry. With current identity and the same principal/context, an attendance-only participant can discard the recovery without decrypting its private draft or suggestions; reading/recovering consumption and its proposal acknowledgement still requires reporting permission.

The company worksite selector validates the current source route, epoch, participant, binding and quoted outbound prompt before continuing this recovery. A still-live consumption recovery may continue after the selector expires; it does not select another worksite or renew the selector. Changing the selected worksite requires explicit cancellation even after the recovery expires, so the selector cannot abandon it under a different route epoch. Company cancellation removes both private records together and rechecks the source-event lease around the close. A rejected **Guardar** from any earlier rejection cannot attempt another save: the explicit review marker must reference the latest rejection receipt.

The default signed identity resolver and the exact corporate wrapper built by the bridge retain their canonical transaction locks during local recovery. Their compact guard reuses the existing member, assignment, approved-participant and binding checks against a fresh Worker read, then checks connection/OWN time validity, source lease and deadline against the SQL clock. An injected identity adapter keeps full re-resolution; a caller flag cannot enable the compact path. The composed memory fixture records query counts and a modeled SQL clock, which do not establish native PostgreSQL or full processor/provider latency acceptance.

Its company composition also runs the canonical signed identity/KYC/binding modules against strict memory SQL and encrypted synthetic messages, including a modeled 225 ms SQL clock and the original 60 second source lease. It does not execute PostgreSQL locks or establish full processor/OWN/Graph latency. No earlier suite/check counter or historical receipt is revised for these new cases. The existing material-consumption workflow test/lint wildcards include this file; a run of that workflow and required native acceptance remain separate release steps.
- The additive native fixture uses an explicitly guarded, owned disposable PostgreSQL database with synthetic canonical identity, real signed callback parsing and encrypted inbox/lease processing. Fifteen groups cover all consumption states, keyset paging, worker reassignment, permissions/revocations, original acknowledgement replay and unchanged stock on reads. It prohibits provider HTTP and closes its pools/database.
- The additive browser fixture renders the exact Next JSX/CSS with synthetic auth/APIs. Twelve cases cover 320/390/768/1280 px, legacy event gaps, receipt/reload recovery, retained unknown UUIDs, denial after visible history/private drafts, and discarded cross-company late responses. It owns and closes only its own IPC server, browser and fixture.
- An additive CI validator binds those receipts to the exact event commit/tree, complete source closures, producer hashes, expected checks and resource cleanup. The existing workspace, access-boundary and measurement suites remain required.

Local/CI acceptance is distinct from real identity presentation/review, customer WhatsApp delivery, and physical field operation. Publication is recorded separately after the final immutable candidate passes CI.

## Current authority at reply delivery

New field receipts include a canonical semantic reply descriptor (`REPORT`, `ATTENDANCE`, `MIXED`, `MENU`, `WITHDRAWAL`, `GENERIC` or the separate `PLAN_IMPORT` role requirement). It binds the signed event and payload, organization, target project, original actor/membership/worker/binding, immutable corporate context and exact final reply digest. A tenant/resource keyed commitment protects the descriptor header before private result decryption. The canonical planner and writer supply it; an inbound field or `send()` option cannot supply or downgrade it. A general menu's canonical choice values also contribute permissions: available attendance transitions expose journey state, and report/consumption actions expose report/catalog availability. These capabilities are added to the reply's base requirement, including journey errors and cancellations that emit a new menu; titles are never interpreted. A new menu generated after a permission is revoked contains only currently available choices. A greeting that preserves a draft emits no new menu. The separate plan importer retains its role requirement and does not emit a general menu with importer data; any future attempt to combine that role-bearing base through this two-capability helper fails closed. Report-only `ESTADO` omits the person's journey; a response containing both journey and reports requires both current permissions. Web ADMIN/DIRECTOR roles do not substitute for the individual's reporting or attendance permission.

Outbound reads that exact durable receipt and checks its descriptor and live canonical participant authority before reservation, after reservation and at the provider's final-before-POST fence. The same canonical transaction holds its participant, assignment, Worker, connection, source and OWN locks through its single POST. A compact guard is available only to the exact two production resolver functions, inside that one transaction after its first full resolution; it reuses canonical member/assignment/participant/binding helpers, a fresh Worker read, current database clock, connection policy, source lease and the descriptor. A custom resolver or caller flag cannot enable it. No guard is carried into another transaction, send or retry, and the original lease is not renewed.

Corporate FIELD/BINDING replay always enters the field receipt reader instead of recovering a private report directly from the company cache. The cache write now shares the field receipt transaction, original source-anchor AAD and exact immutable projection CAS. A missing legacy cache may store the already authorized original result without adding a descriptor to that historical receipt; an existing cache is compared and retained without rewriting its ciphertext. This removes the third full company resolution previously used only to duplicate the result. The production composition remembers only which trusted adapter actually produced a result in the current process context; outbound still performs its complete canonical authorization, and other routes retain their existing fallback and KYC priority.

Legacy receipts are not retagged. Known report/attendance acknowledgements retain their specific permission. Ambiguous `CONVERSATION` replies can use only the existing canonical conversation reader when its binding and exact source event still match. A next-state `MENU` alone is insufficient: a signed attendance command may have produced a private journey error, so it still requires attendance permission. A signed `MENU`/`AYUDA`/`HOLA`/`CANCELAR` text command identifies a legacy menu, but its exact authenticated current choice values still add attendance/report requirements to that base. Unknown or malformed choices and interactive/unknown sources require a fresh command instead. An old mixed status requires both capabilities. An unknown or stale ambiguous reply is denied and kept; a fresh command remains available. This compatibility classification can decrypt the current same-source conversation in memory to determine its purpose, but never returns its draft or decrypts the old dispatch body before the resulting permission check. New authenticated headers remove that ambiguity. A derived expiry observation does not rewrite an earlier private acknowledgement or authorize resending it.

The authenticated descriptor is serialized as an explicit ordered list of field/value pairs, with the immutable receipt kind and recovery context/deadline in the commitment tuple. JSONB object-key ordering cannot change its authentication or reservation digest. A coherent REPORT-to-MENU field-pair substitution or partial header removal is rejected, rather than being interpreted as a legacy receipt.

An expired `CONSUMPTION_RECOVERY` source may produce only the exact internal expiry feedback when its authenticated receipt header and the current same-principal recovery/prompt headers match and a fresh SQL clock/source lease confirms the observation. Expired dispatch, conversation, sidecar and company cache bodies are not decrypted to produce that feedback. Missing/cancelled/foreign recovery headers cannot claim that a draft was retained. A private summary crossing its deadline after preparation or reservation is denied; it is never automatically transformed into feedback after a reservation. The final provider fence reads the database clock after awaited marker/OWN work as well. Existing proposal acknowledgements remain a separate kind and do not become expiry messages.

If that source already has an outbound marker, the expiry path only observes the original marker. It leaves its request, state, body and ciphertext untouched, returns `replySent: false` for the current feedback and records `replyObservation: ORIGINAL_REPLY_OBSERVED` with the original reply state. A previous SENT is not a claim that the new feedback was sent; prior SEND_STARTED/SEND_UNKNOWN uncertainty and its last error are retained.

`SEND_STARTED`, `SEND_UNKNOWN`, `SENT` and status-observed markers remain at most once: denial, permission restoration or an expired lease cannot lease or send them again. Safe cancellation and new MENU/attendance commands remain independently usable. None of these read/delivery changes approves a report, changes stock or certifies identity.

The new self-contained field/outbound suites exercise the real production factory, canonical corporate/worker/KYC/binding modules and provider request serializer against strict synthetic memory SQL and synthetic fetch, including revocation around awaited work, descriptor/commitment corruption, atomic cache rollback and replay. Memory query counts are not native lock, full OWN latency, provider delivery, production P95 or physical worksite acceptance. The original 23 native/110 graph contracts and all historical producer/workflow pins remain separate, unchanged requirements. A complete current-candidate native run must retain the original 60 s lease and agreed 225 ms SQL/200 ms Graph delays through POST and final processing before claiming that controlled budget passes.
